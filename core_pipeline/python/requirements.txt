# Upper bound is load-bearing, not cosmetic: transformers 5.13.0 registers TrOCR's
# model_type ("vision-encoder-decoder", loaded internally by magi via TrOCRProcessor)
# in TOKENIZER_MAPPING_NAMES pointing at the generic TokenizersBackend class, which can
# only build from a tokenizer.json -- and microsoft/trocr-base-printed has never shipped
# one (only vocab.json+merges.txt). AutoTokenizer.from_pretrained then raises a
# misleading "need sentencepiece or tiktoken" ValueError that has nothing to do with
# sentencepiece (verified: neither package is the cause). Confirmed present through at
# least 5.14.1 and unfixed on transformers main as of 2026-07; no known upper bound
# where it's resolved. ml_region_lib.py's load_semantic_model() also carries a runtime
# shim (re-registers the mapping entry to RobertaTokenizer) as a second, independent
# layer for any environment where this upper bound can't be guaranteed -- e.g. the
# Kaggle deployment notebook, which pins its own transformers version separately from
# this file. Either fix alone is sufficient; both verified locally against the actual
# failing call on both a pre- and post-regression version before shipping.
# sentencepiece + protobuf: needed by the NLLB local-translator tokenizer
